# Job Watcher Playbook

Reference for maintaining this project and adding new company pipelines.

---

## What This System Does

Monitors 120 company career sites every 30 minutes via GitHub Actions. Filters for India-based **.NET/C#** and **AI/ML/Python** software engineering roles — either track qualifies, a job doesn't need both — and sends Telegram + email alerts only for jobs not seen before, each one tagged `[.NET / C#]` or `[AI / ML / Python]` (or both, for a genuinely hybrid role) so the two tracks are easy to tell apart in one feed. Each company has its own fetcher, registry entry, seen-jobs file, and config section; orchestration is shared.

---

## Filter Layers

**3 layers apply to every company. Companies where the shared skill check is too broad add a 4th (opt-in only).**

**Layer 1 — Location**
- Job location must contain "India"
- Must not be Chennai, Tamil Nadu, Pune, Chandigarh, Kochi, Kerala, Trivandrum, Lucknow, Nagpur, Madurai, Kolkata, or Indore (configured per company via `exclude_locations`)

**Layer 2 — Title**
- Title must match the software engineer family (`matching.title_family` in config)
- Title must not match `matching.exclude_terms` (no interns, managers, hardware, etc.)

**Layer 3 — Skills**
- Description must contain at least one **primary** skill from EITHER named group in `matching.primary_skills` (config.yaml) — a job qualifies via one track, not both:
  - **`.NET / C#`**: `.NET`, `C#`, `ASP.NET`, `Web API`, `SQL Server`, `T-SQL`, `Entity Framework`, `dotnet`
  - **`AI / ML / Python`**: `LangChain`, `LangGraph`, `RAGAS`, `Langfuse`, `LangSmith`, `CrewAI`, `vector database`, `ChromaDB`, `Pinecone`, `generative ai`, `large language model`, `retrieval augmented generation`
  - Broad-only terms in `matching.skills` (Azure/Angular/TypeScript/React/Python/machine learning/Golang/etc.) never pass alone — they're too common in unrelated postings.
  - This same grouping is the source of the `[.NET / C#]` / `[AI / ML / Python]` tag attached to every alert (`src/matcher.py::_derive_tags`) — a job mentioning terms from both groups gets both tags.
  - **Never add bare `AI`, `ML`, `RAG`, `LLM`, `GPT`, or `Go` to either group** — matcher.py's substring check isn't word-boundary aware, and those short tokens are substrings of ordinary words ("RAG" ⊂ "storage"/"average"/"garage", "Go" ⊂ "going"/"ongoing"/"algorithm", "ML" ⊂ "HTML"). Use the full distinctive term instead (`Golang`, `generative ai`, `large language model`, ...) — same signal, no false positives.

**Layer 4 — Tech in description (Wells Fargo, Accenture, Infosys, Cognizant, Capgemini, TCS, Wipro, HCLTech, DXC, Citi, State Street, First American, Adobe, Sabre, Autodesk, Micron, eBay, Oracle, Lowe's, Bank of America, LTIMindtree, Persistent Systems, Genpact, IBM, Tech Mahindra, Virtusa, Hexaware, Societe Generale, Charles Schwab — opt-in, do not add to new companies by default)**
- Description must explicitly contain a **narrow** term from either track (`require_tech_in_description` in config): `.NET`/`C#`/`ASP.NET` for the .NET track, or the same hard AI list as Layer 3's `AI / ML / Python` group — narrower than Layer 3's broader `.NET / C#` group, which also passes on SQL Server/EF/Web API alone
- Originally added for IT-services shops whose generic titles ("Senior Software Engineer", "Software Engineer L3") give no reliable tech signal, where Layer 3's broader skill list was letting non-.NET roles through (e.g. HCLTech: Cisco Unified Comms, ServiceNow, GCP, Azure-monitoring roles that happened to mention SQL Server/EF); since extended to direct employers (Citi, State Street, First American, Adobe, Sabre, Autodesk, Micron, eBay, Oracle, Lowe's, Bank of America, LTIMindtree, Persistent Systems, Genpact, IBM, Tech Mahindra, Virtusa, Hexaware, Societe Generale, Charles Schwab) as a general precision tightener wherever the broader skill list alone risks false positives
- Activated by the company's registry metadata and applied centrally by `run_company.py` after the shared matcher.
- **Retired: title-based matching (`require_tech_in_title`).** Every company that used it now uses description matching instead — title text turned out to be too sparse a signal at IT-services shops (many real .NET roles carry a generic level-banded title with the tech named only in the JD body)

Deduplication: jobs already in `seen_jobs_<company>.json` are never re-alerted (all companies).

## Architecture

```
config.yaml                    ← all config (search params + shared matching rules)
src/
  company_registry.py          ← inventory + conservative fetch capabilities
  run_company.py               ← one generic pipeline implementation
  run_all.py                   ← bounded launcher (10 at a time by default)
  matcher.py                   ← shared filter engine (title family → exclude → skills)
  notifier.py                  ← Telegram + email alerts
  <company>_fetcher.py         ← data source: fetch_jobs() + fetch_job_description()
seen_jobs_<company>.json       ← deduplication state
.github/workflows/watcher.yml  ← invokes the launcher and commits state
```

**matcher.py expects every fetcher to export exactly three things:**
```python
class RateLimitError(Exception): ...
def fetch_jobs(keyword, location, *, num, start, sort_by, timeout) -> list[dict]: ...
def fetch_job_description(application_url, timeout) -> tuple[str, str]: ...
```

Each job dict must have: `id`, `title`, `location`, `posting_date`, `application_url`.

---

## Filter Pipeline (All Companies)

```
fetch_jobs()
    └─ is_india_job()                  skip non-India silently
    └─ exclude_locations check         skip Chennai/Pune/Tamil Nadu silently
    └─ passes_exclude_check()          [exclude] tag in near-miss log
    └─ passes_title_family_check()     [title family] tag in near-miss log
        └─ known-ID check              skip detail call for alerted jobs
        └─ fetch_job_description()
            └─ primary_skills check    [broad-only] / [react-only] / [skill] tags
```

**Layer 4 (opt-in, never added by default):**
```
    └─ require_tech_in_description check [desc-tech] tag in near-miss log
```
Implemented once in `run_company.py`; registry metadata enables it for companies whose config contains `require_tech_in_description`.

## How to Add a New Company

> **Every company is different.** The steps below capture what worked across 6 past integrations. They are a starting point, not a checklist. Each new ATS will have its own quirks — different API shapes, bot protection, date formats, title conventions, or pagination schemes. Read what the new system actually does before reaching for a copy-paste from an existing fetcher. The goal is always accurate job alerts; the playbook is there to save time, not to constrain good judgment.

> **Read "Filter Layers", "Scope Expansion: AI/ML/Python Track Added (2026-08-30)", and "Company Coverage Audit (2026-08-30)" below before starting.** Three things that changed and matter for every new company you add:
> 1. **This watcher targets TWO tracks, not one.** `matching.title_family`/`skills`/`primary_skills`/`exclude_terms` in `config.yaml` are GLOBAL — shared by every company — so you do not add per-company title/skill lists. The only per-company decision is whether to enable Layer 4 (`require_tech_in_description`), and if you do, its term list must offer both the `.NET`/`C#`/`ASP.NET` terms AND the AI/ML hard terms (copy the list straight from any existing company's `require_tech_in_description` block, e.g. `wellsfargo_search` — do not just add the `.NET` terms because that's what you see most often in the file).
> 2. **Do not add bare `AI`, `ML`, `RAG`, `LLM`, `GPT`, or `Go` anywhere** — see the false-positive rationale in "Scope Expansion" below. If a company's real postings need a new skill term you haven't seen before, use the full distinctive form.
> 3. **If you add a term to `primary_skills` (either group), it MUST also be added to `skills`.** These are two independent checks a job must pass both of — this exact gap was a real bug caught during rollout (see "Scope Expansion" below). This should rarely come up when just adding a new company, since `primary_skills`/`skills` are global and probably already cover your company's stack, but if you find a legitimate match failing only because of `skills`, check this invariant first before assuming the company's fetcher is broken.
>
> New-company work itself (fetcher, registry, config, seen-jobs file) is orthogonal to all of this — you're plugging a new data source into filtering rules that already understand both tracks.

### Step 1 — Identify the ATS (10–20 min)

Open the careers page in a browser, search for a role, open DevTools → Network tab, look at XHR/fetch calls. Ask:

- **Does `requests.get/post` return job data?** → REST API approach (fast, like Optum/Wells Fargo)
- **Are all API responses empty or 403?** → Playwright needed (like Honeywell)
- **Is Chromium blocked?** → Use Firefox (Honeywell lesson)

### Step 2 — Map the response structure

Find: job ID field, title field, location field, posting date field, application URL field. These vary per ATS — check the raw JSON/HTML before writing code.

Watch out for:
- Relative dates ("Posted 3 Days Ago") — need conversion to `YYYY-MM-DD`
- Abbreviated titles ("Engr" instead of "Engineer") — may need additions to `title_family` in config
- JavaScript-rendered descriptions — plain `requests` may return empty; need Playwright or a JSON detail API

Copy the closest existing fetcher as a starting point:
- REST JSON → copy `wellsfargo_fetcher.py`

- Playwright needed → copy `honeywell_fetcher.py`

Always include:
- Retry loop (3 attempts, exponential backoff)
- `RateLimitError` on 429 or persistent failure — matcher.py catches this and logs a warning instead of crashing
- Browser-like `User-Agent` header

### Step 4 — Register the company

Add one `CompanyPipeline` row to `src/company_registry.py` through `_PIPELINE_DATA`. The slug drives the conventional fetcher, config, and state names. Set the display source and whether the narrow description filter is enabled.

Also classify only capabilities you verified:

- Add the slug to `_IGNORES_KEYWORDS` when the API returns the same pool for every query. This makes the generic runner issue one query pass instead of six identical passes.
- Add it to `_SUPPORTS_LOCATION`, `_INLINE_DESCRIPTIONS`, or `_NEWEST_FIRST` only after observing that behavior.
- Conservative defaults are intentional. Never use alerted-job IDs as a pagination watermark: they do not include filtered-out listings, and config changes can make old jobs newly eligible.

### Step 5 — Add to `config.yaml`

Add a new section before `notifications:`:
```yaml
<company>_search:
  max_listings: 200
  inter_page_delay: 0.2       # be polite; 0.1 for fast APIs
  keywords: *default_keywords
  locations: *india_locations
  exclude_locations: *default_exclude_locations
  # DO NOT add require_tech_in_description unless explicitly asked
```

Check if the company's ATS uses server-side keyword filtering (Workday does) or ignores keywords (Siemens doesn't). If it ignores keywords, all keywords will return the same result set and deduplication will handle it.

### Step 6 — Leave the workflow alone

The workflow calls `run_all.py`, which discovers the registry, and stages tracked `seen_jobs*.json` files with a pathspec. Adding a registry entry and state file is enough. If the company needs Playwright, Firefox is already installed and cached.

### Step 7 — Create `seen_jobs_<company>.json`

```json

```

Commit this file alongside everything else.

### Step 8 — Test locally, then push

```bash
py src/run_all.py --validate --companies <company>
py src/run_company.py <company>
```

Verify:
- Non-zero jobs fetched with India locations
- Near-miss log shows `[title family]`, `[skill]`, `[broad-only]` tags firing correctly — no obvious false positives
- Matches are genuinely .NET/C# OR genuinely AI/ML/Python (see "Scope Expansion" below — Python/LangChain/RAG jobs are legitimate matches now, not false positives; a bare "Java" or "cloud-native" role with no hard signal from *either* named `primary_skills` group is what should NOT slip through)
- Every matched job's `tags` field is non-empty and correct (`[.NET / C#]`, `[AI / ML / Python]`, or both) — sanity-check a few real matches through `format_message`
- Pune/Kochi/Chandigarh/Chennai/Tamil Nadu not in any matched result's location
- Alert fires (or "not sent (no new matches)" if all already seen)

## GitHub Actions

- `run_all.py` runs all 74 registry entries with **bounded concurrency** (10 workers by default; configurable with `--workers` or `JOB_WATCHER_WORKERS`)
- One company failure does not cancel peers, but the launcher exits non-zero after all work finishes so the workflow is visibly failed
- Firefox Playwright is **cached** via `actions/cache@v4` on `~/.cache/ms-playwright`
- Tracked `seen_jobs*.json` and `pipeline_failures.json` changes are committed after each run with `[skip ci]`, including failed runs
- The workflow runs every 30 minutes and also supports manual `workflow_dispatch`
- Queued runs fast-forward before scanning; state pushes retain the union merge driver and three-attempt rebase/push loop

## Optimization Learnings (2026-07-04)

- **Filter known IDs before detail fetches.** The alert ledger already guarantees these jobs cannot notify again, so re-downloading their descriptions was pure cost. Keep the check after cheap location/title filters for useful diagnostics, but before detail HTTP.
- **Do not stop pagination using alert IDs.** Seen files contain only alerted matches, not every processed listing. They are not scan watermarks, and older filtered jobs may become eligible after rule changes.
- **Model ignored query parameters explicitly.** Eighteen adapters ignore caller keywords. Registry capability metadata now collapses those to one query pass without weakening the conservative default for other adapters.
- **Bound pipeline concurrency globally.** Seventy-four simultaneous processes caused unnecessary memory/network pressure and made shared failure-state writes race. A ten-worker thread pool keeps independent pipelines moving while bounding load.
- **Delivery and dedup state are one transaction.** If every configured notification channel fails, do not advance seen state. Otherwise a transient Telegram/Gmail outage permanently loses the alert. With no channels configured, local runs retain historical state-advance behavior.
- **Keep failure state thread-safe and failures visible.** Failure-counter read/modify/write is locked; individual errors are recorded while the launcher continues, then the overall process exits non-zero.
- **Centralize orchestration, not ATS behavior.** The registry and generic runner removed 73 duplicated entry points. Fetchers remain separate because their pagination, authentication, bot protection, and location semantics genuinely differ.
- **Use YAML anchors for repeated policy.** Shared keywords, India location, and exclusions now have one source while company-specific overrides remain explicit. Parsed config was compared before/after and is identical.

## Scope Expansion: AI/ML/Python Track Added (2026-08-30)

The target candidate's skill profile grew a second pillar — production Python AI/LLM engineering (LangChain, LangGraph, RAG pipelines, vector DBs, RAGAS, Langfuse/LangSmith, CrewAI) — alongside the original 6-year .NET/C# background this watcher was built around. Rather than replace the .NET targeting, matching was broadened additively: a job now qualifies via EITHER track.

- **`matching.primary_skills` changed shape: flat list → named groups.** It's now `{".NET / C#": [...], "AI / ML / Python": [...]}` instead of one flat list. `find_matching_jobs` flattens it for the pass/fail check (identical gating behavior — at least one term from any group) but also keeps the mapping to derive which group(s) a match came from.
- **Every alert now carries a `[tag]` prefix** (`[.NET / C#]`, `[AI / ML / Python]`, or both for a genuinely hybrid role) so the two tracks are easy to tell apart in one combined Telegram/Gmail feed, instead of running two separate watchers. Source: `matcher.py::_derive_tags`, rendered by `notifier.py::format_message`. A job kept via the fail-open path (description fetch failed, so no skill check actually ran) is tagged `Unverified` rather than defaulting to either real tag.
- **Do not add bare `AI`, `ML`, `RAG`, `LLM`, `GPT`, or `Go` as skill/keyword terms anywhere in this file.** `matcher.py`'s substring check is not word-boundary aware, and every one of these is a substring of extremely common words in ordinary job descriptions: `"RAG"` ⊂ "sto**rag**e"/"ave**rag**e"/"ga**rag**e", `"Go"` ⊂ "**go**ing"/"on**go**ing"/"al**go**rithm", `"ML"` ⊂ "HT**ML**". Distinctive multi-word/proper-noun terms (`LangChain`, `generative ai`, `large language model`, `Golang`, ...) carry the same signal with zero false-positive risk — this was verified by design review, not hit as a live bug, but the risk is real enough (and tempting enough to "helpfully" re-add later) that it's recorded here rather than only in a code comment.
- **Layer 4 (`require_tech_in_description`) got the same AI/ML term list added to all ~28 companies that use it**, alongside their existing `.NET`/`C#`/`ASP.NET` terms — otherwise a generic-titled IT-services posting (e.g. plain "Software Engineer" at TCS/Infosys/Wipro) that explicitly names LangChain/RAG work in the JD body would pass Layer 3 but still get rejected at Layer 4, since that layer's term list hadn't been told about the new track.
- **Bug caught during rollout verification: `skills` and `primary_skills` are two independent checks — a job must pass BOTH.** For the .NET track every `primary_skills` term is also present in `skills`, so this is invisible. The initial AI/ML rollout only added the hard AI terms (LangChain, LangGraph, etc.) to `primary_skills` and forgot to duplicate them into `skills`, so a real-shaped JD naming only tool names ("Build a RAG platform using LangChain and LangGraph with a ChromaDB vector database") — no incidental "Python"/"machine learning" mention — was silently dropped by the broad `skills` gate before `primary_skills` was ever consulted. Caught by re-running the actual pipeline end-to-end (not just the unit tests, whose AI fixture happened to also say "Python") when asked to double-check the tagging claim. Fixed by duplicating all 12 hard AI terms into `skills`; `test_find_matching_jobs_keeps_ai_role_with_no_soft_skill_overlap` in `tests/test_matcher.py` guards this going forward. **Any future primary_skills group must have every one of its terms also listed in `skills`.**

## Batch Onboarding Wave 1 (2026-08-30): 10 Companies Added in Parallel

Followed up on the audit above by building the 10 easiest-to-classify gaps in parallel (each as an independent agent, briefed to read this playbook first): **Groww, Razorpay, CRED, Meesho, Paytm** (Greenhouse/Lever — confirmed via public documented REST APIs), **eClerx** (Oracle HCM CE — a third known example of this ATS, alongside Hexaware/Chubb/Icertis), and **Macquarie, MUFG, ING, SAP Labs** (Workday ×3, SuccessFactors — patterns this repo already had ~15 solved examples for). **Toptal, Turing, and Trilogy were explicitly skipped** — recon found Toptal/Turing expose only their own tiny corporate-HQ hiring boards (e.g. "CEO, AI Services"), not the freelance-marketplace gig listings the original "(Remote)" framing implied, and neither that nor Trilogy's unusual apply-and-screen funnel fits this watcher's "new job posting" alert model at all. Decision: skip all three rather than build something technically present but functionally wrong. **Coordination approach for future waves:** each agent was told to build ONLY its own new files (`src/<slug>_fetcher.py`, `seen_jobs_<slug>.json`) and to report back — not apply — the exact `_PIPELINE_DATA` row, capability-set memberships, and `config.yaml` block. This avoided any concurrent-edit conflicts across 10 simultaneous agents touching the same files, and let one person sanity-check consistency (alphabetical ordering, correct capability-set membership, no duplicate slugs) before merging. **Reuse this pattern for future batches** — do not let parallel company-onboarding agents edit shared files directly.

### Critical fix: Playwright-based fetchers have been silently broken in every production run since at least 2026-08-28

While investigating the "bunched alerts" complaint above, `gh run view --log` on the live triggered-verification run (post-Wave-4 deploy) showed **every one of the 8 Playwright-based companies fetching 0 jobs**, each logging `RateLimitError: ... cache fill failed: It looks like you are using Playwright Sync API inside the asyncio loop.` Checked historical runs going back to 2026-08-28 (before this session's changes even started) — **100% of scheduled runs show this same failure for these companies.** The Wave 3 entry above dismissing this exact error as "a health-check-script artifact, not a production issue" was wrong: it never actually checked a real scheduled `run_all.py` production run's log, only an isolated fresh-process re-test.

**Root cause, confirmed empirically (not just theorized) via local reproduction**: `run_all.py` submits every company to one shared `ThreadPoolExecutor`, which reuses a fixed set of OS threads across the full company list as tasks complete. Each of the 8 Playwright-based fetchers (`bnpparibas`, `honeywell`, `ibm`, `natwest`, `perfios`, `servicenow`, `techmahindra`, `virtusa`) keeps its browser open as a **module-level singleton for the whole process's life** (`atexit`-only cleanup — deliberate, to avoid relaunching Firefox on every call). The first time any one of these modules calls `sync_playwright().start()` on a given OS thread, it succeeds and binds an asyncio event loop to that thread for good. If the pool later reuses that *same* thread for a *different* Playwright-based company's `_ensure_browser()` call, Playwright's sync API sees the leftover loop and refuses outright.

Reproduced directly: running all 8 real fetchers' `fetch_jobs()` concurrently with `ThreadPoolExecutor(max_workers=4)` (one thread per company, no reuse) — **0 failures**. Running the same 8 through `max_workers=3` (forcing at least 2-3 threads to each handle multiple different Playwright companies) — **3/8 failed** with the exact production error. Running all 8 through `max_workers=8` (one dedicated thread per company again) — **0 failures, every company returned its real job count** (BNP Paribas 616, IBM 665, Honeywell 200, Tech Mahindra 76, NatWest 56, ServiceNow 39, Perfios 3). This conclusively isolates the trigger to *thread reuse across two different Playwright-based modules*, not "any two Playwright instances alive at once" (they can run fully concurrently on separate threads with zero issue).

**Fix**: `company_registry.py` gets a new `uses_playwright: bool` field on `CompanyPipeline` and a `_USES_PLAYWRIGHT` frozenset (the 8 slugs above). `run_all.py::run_companies()` now splits the company list into two groups and opens two separate `ThreadPoolExecutor`s: the general pool (still sized by `--workers`) for everyone else, and a **dedicated pool sized 1:1 with however many Playwright-based companies are selected**, guaranteeing every one of them gets its own OS thread for the entire run and never shares it with another Playwright-based module. Both pools run concurrently with each other. Verified end-to-end via the real `run_all.py` CLI (not just direct fetcher calls) — all 8 companies returned `ok` with real, substantial fetch counts and zero asyncio-loop errors in the full log.

This means **Honeywell, Tech Mahindra, Virtusa, BNP Paribas, and NatWest have likely never sent Shivangi a single real alert since being added** — their entire pipeline was silently returning 0 jobs on every single scheduled run, invisibly (no pipeline failure — a clean 0-job "success" looks identical to a genuinely quiet company in the logs, which is exactly why this stayed hidden). Perfios and ServiceNow (added this wave) would have had the identical problem from their very first run had this not been caught during the post-deploy live-verification check. This is a strong argument for periodically re-running the full health check against **real scheduled-run logs**, not just isolated fresh-process re-tests — the two environments do not behave the same way once thread-pool reuse is involved.

Lesson for future Playwright-based fetchers: any new one must be added to `_USES_PLAYWRIGHT` in `company_registry.py` (there's now a dedicated registry test, `test_registry_flags_playwright_backed_fetchers`, enforcing the exact expected set) — forgetting this silently reintroduces the exact same bug for that company.

**Correction, same day: the dedicated-thread-per-company fix above was not sufficient.** Deployed it, triggered a live verification run (`33476619607`), and 7 of the 8 companies *still* failed with the identical "asyncio loop" error — all within a ~3 second window right at the start of the run, meaning they were genuinely racing each other on their (now-guaranteed-separate) dedicated threads. This never reproduced locally on a multi-core Mac; it reproduced reliably on GitHub Actions' CPU-constrained runner. Conclusion: thread reuse was one real trigger (fixed, keep it), but simultaneous `sync_playwright().start()` calls from different threads racing under CPU contention is a *second*, independent trigger the local repro never exercised.

**Real fix**: added `src/_playwright_startup.py`, a single module-level `threading.Lock()` (`STARTUP_LOCK`). Every one of the 8 Playwright-based fetchers now wraps only its one-time `sync_playwright().start()` + `.launch(...)` call in `with STARTUP_LOCK:` — serializing just the brief startup moment process-wide, while the actual per-company scraping that follows (page navigation, extraction) still runs fully concurrently across companies, since the lock is released immediately after launch. Guarded with a new test (`tests/test_playwright_startup_lock.py`) that AST-parses each Playwright-backed fetcher and confirms its `sync_playwright().start()` call is genuinely inside a `with STARTUP_LOCK:` block, not just that the string appears somewhere in the file — so a future Playwright-based fetcher that forgets to hold the lock around its actual launch call fails CI immediately instead of silently reproducing this bug.

**Lesson**: for concurrency bugs, a clean local repro is necessary but not sufficient — always verify the actual fix against a real triggered production run before considering it closed. This is the second time this exact bug fooled a "confirmed fine in isolation" check (see the original, wrong Wave 3 entry above); the pattern to watch for is any Playwright/thread-safety issue where the failure is sensitive to CPU contention or scheduling timing, since a fast local machine can mask races a constrained CI runner exposes reliably.

**Correction #2, same day: the shared-lock fix above ALSO failed in production.** Deployed it, triggered a second live verification run (`33481734513`), and the exact same 7 companies failed again with the identical error, at nearly the same relative moment (~5 seconds into the run) as before the lock existed — meaning `STARTUP_LOCK` had no observable effect. Read Playwright's actual `PlaywrightContextManager.__enter__` source directly (`playwright/sync_api/_context_manager.py`) rather than continuing to guess: the check is `asyncio.get_running_loop()` (thread-local by design) followed by `self._loop.is_running()` on a freshly created loop — which should be structurally impossible to trip on a guaranteed-fresh, never-reused, lock-serialized OS thread. Since two independent, individually-reasoned fixes for two different theorized mechanisms both failed identically in the same real environment, the honest conclusion is the exact trigger on GitHub Actions' runner was never fully identified — the local machine's inability to reproduce this bug at all (not even without any fix) made every "local pass" a false signal of confidence.

**Real fix**: stopped trying to make threads safe for this and sidestepped the entire class of problem. `run_all.py` now runs each of the 8 Playwright-based companies in its own **subprocess** (`subprocess.run([sys.executable, "run_company.py", slug, "--config", ...])`) instead of a thread in any pool — a fresh OS process has no possible shared Python state with any other company's process (no shared threads, no shared module-level singletons, no shared event loop of any kind), which removes every mechanism that could cause this regardless of which one was actually responsible. `STARTUP_LOCK` was left in place (harmless, zero-cost with one thread per process) as defense in depth. General (non-Playwright) companies are unaffected — still run in-process via the shared thread pool, exactly as before.

**Lesson, stated more sharply this time**: when a bug cannot be reproduced locally at all, "it doesn't happen in my test" carries zero evidentiary weight for whether a fix works — only a real triggered production run is evidence, and even a clean one should be treated cautiously until it's been seen at least once. When two different fixes for two different theorized root causes both fail identically, stop trying to out-theorize the specific mechanism and reach for the strongest structural guarantee available (full process isolation) rather than a third narrower patch.

### Correction #3 — the actual root cause, found by finally reading the FIRST exception instead of only the LAST one

Subprocess isolation (attempt 3) *also* failed identically in production (run `33489814084`). At that point the "different Playwright instances collide" theory had failed three independent, structurally-sound fixes in a row — a strong signal the theory itself was wrong, not that a fourth patch was needed. Went back to the raw log and, instead of grepping for `"asyncio loop"` (which is what every previous pass had done), grepped for `"search fetch failed"` / `"rate-limited for"` **excluding** that string, to see what each company's *first* attempt actually failed with, before any retry:

- `NatWest`: `BrowserType.launch: Executable doesn't exist at .../chromium_headless_shell-1234/...` — completely different browser (Chromium, not Firefox!) and a completely different, much simpler cause: **the workflow's `playwright install firefox` step never installs Chromium at all**, and NatWest deliberately uses Chromium (its Cloudflare challenge blocks Firefox — see the Wave 3 entry). Not a race, not a cache issue — just a browser that was never installed, full stop, every single run since the day NatWest was added.
- `Honeywell`, `Tech Mahindra` (no internal retry — the raw error surfaces directly): `BrowserType.launch: Executable doesn't exist at .../firefox-1538/firefox/firefox` — the **exact same bug class already found and fixed the same day in the sibling `ai-job-watcher` repo**: `requirements.txt` had `playwright>=1.44` (unpinned), so `pip install` resolved whatever's newest (1.62.0) each run; the browser cache key only hashes `requirements.txt`'s *text*, which never changed, so a stale/wrong-build Firefox kept getting restored from cache instead of the build `1.62.0` actually needs.
- `BNP Paribas`, `Perfios`, `ServiceNow`, `Virtusa` (**do** have an internal `for attempt in range(3):` retry around browser startup): same underlying `firefox-1538` executable-missing error on attempt 1 — but it was **never visible in any log from any of the first three fix attempts**, because `_ensure_browser()`'s original code was:
  ```python
  if _browser is None:
      with STARTUP_LOCK:
          _pw = sync_playwright().start()   # succeeds -- returns a live instance
          _browser = _pw.firefox.launch(headless=True)   # fails: wrong build cached
      atexit.register(_shutdown_browser)
  ```
  When `.launch()` raises, `_pw` is left pointing at a **live, never-stopped** Playwright instance (its background dispatcher greenlet+loop keeps running — `_shutdown_browser` is only `atexit`-registered, and that registration line is never reached on failure). The caller's retry loop catches the exception and tries again on attempt 2, which calls `_ensure_browser()` again — `_browser` is still `None`, so it calls `sync_playwright().start()` **again, on the same thread, while attempt 1's own instance is still alive** — which is genuinely, correctly detected by Playwright as "Sync API inside the asyncio loop" (this really is the one situation that check exists to catch). The retry loop's `last_exc` variable then gets overwritten with this second, unrelated-looking exception, and the original `firefox-1538` error — the actual root cause — is silently discarded and never printed anywhere. **Three straight fix attempts chased the symptom (the masking exception) because the masking exception was the only one anyone had ever seen.**

**Real fix (this time addressing the actual cause)**:
1. `requirements.txt`: pinned `playwright==1.62.0` (same fix as `ai-job-watcher`) — any future version bump now changes the cache key too, so the cache can never silently drift out of sync with the installed package again.
2. `watcher.yml`: `playwright install firefox` → `playwright install firefox chromium` (NatWest needs Chromium and it was simply never being installed); replaced the old bare `if cache-hit != true` gate with a real verify step that actually **launches both browsers** via a one-line Python smoke test and reinstalls if that fails — catches a stale/wrong-build cache even if the pin is ever loosened again, same pattern just added to `ai-job-watcher`.
3. **The actual bug**: every one of the 8 `_ensure_browser()` implementations now wraps `.launch(...)` in `try/except`, and on failure calls `_pw.stop()` and resets `_pw = None` before re-raising — so a caller-level retry always starts from a clean slate instead of colliding with a leaked, still-running instance from the failed attempt. This is the fix that actually matters going forward: even if a browser launch fails for some *future*, unrelated reason (a transient runner resource blip, a real new Playwright/browser incompatibility), the retry will now fail with the **true, original error message**, not a confusing masked one — which is what should have made this whole investigation take 10 minutes instead of most of a day.

**Lesson, sharper still**: when investigating a retried operation's failure, always check what the *first* attempt's exception actually said, not just the exception that finally propagated out after all retries were exhausted — a retry loop that doesn't log each attempt, or a bug (like the leaked `_pw` here) that makes attempt 2's failure look completely different from attempt 1's, will actively mislead you toward fixing the wrong layer. Three fix attempts (thread isolation, a startup lock, full subprocess isolation) were all individually well-reasoned and individually correct answers to *a* problem — just not the one that was actually happening. The tell, in hindsight, was that all three kept failing identically no matter how thoroughly the "concurrent Playwright instances collide" theory was addressed; that should have been the cue to question the theory itself much sooner rather than escalate to a stronger version of the same fix.
